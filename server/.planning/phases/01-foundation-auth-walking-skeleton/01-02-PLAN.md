<objective>
Grow the walking skeleton's single-table database into the complete data model the rest of the project
is built on, and make the public mechanic directory a self-maintaining projection rather than a table
someone has to remember to update.

**User story (MVP):** **As a** client browsing for a mechanic, **I want to** see a directory that
always reflects who is actually available right now, **so that** I never book someone who has
deactivated their account or contact a listing that went stale.

Purpose: `01-01` proved the architecture on one table. This plan proves it holds for the whole schema —
including the two things SQLite does differently from the Postgres source (partial unique indexes for
double-booking prevention, and triggers with no shared stored function to call). Phase 2's booking
logic, Phase 3's admin actions, and Phase 4's notifications all write into tables this plan creates.
Output: The full nine-table schema in a real SQLite file, six triggers keeping `public_mechanics`
correct, and two test files proving both.
</objective>

<inherited_contract>
`01-SKELETON.md` and `01-01-PLAN.md`'s architectural contract are fixed. This plan consumes them and
must not renegotiate them. The conventions that bind every table below:

| Concern | Fixed convention (from 01-01) |
|---|---|
| Identifiers | Postgres `UUID` ports to SQLite `TEXT`; values minted with `crypto.randomUUID()` in application code (SQLite has no `gen_random_uuid()`) |
| Timestamps | Postgres `TIMESTAMP WITH TIME ZONE` ports to `TEXT` holding ISO-8601 UTC, defaulted with the SQLite expression `strftime('%Y-%m-%dT%H:%M:%fZ','now')` |
| Booleans | Postgres `BOOLEAN` ports to `INTEGER` 0/1 via Drizzle `{ mode: 'boolean' }` |
| JSON | Postgres `JSONB` ports to `TEXT` holding a JSON document, defaulted to the two-character empty-object literal |
| Dates / times | Postgres `DATE` ports to `TEXT` as `YYYY-MM-DD`; `TIME` ports to `TEXT` as zero-padded `HH:MM:SS`. Zero-padding is load-bearing — the ported time-ordering CHECK constraints compare these as strings, and an unpadded `9:00` sorts after `10:00` |
| String-length CHECKs | Postgres `char_length(...)` ports to SQLite `length(...)`; `BETWEEN a AND b` ports unchanged |
| Literal value sets | Declared once as an exported `as const` array and derived into both the Drizzle column constraint and the TypeScript type — never duplicated (`ROLES` in 01-01 is the pattern to follow) |
| Foreign keys | Enforced only because `src/db/client.ts` runs `PRAGMA foreign_keys = ON`; every table below depends on that pragma already being in place |

Existing symbols from 01-01 that this plan extends rather than redefines: `profiles`, `ROLES`, type
`Role` (all in `src/db/schema.ts`); `createDb`, `runMigrations`, `makeTestDb`.
</inherited_contract>

<research_divergence>
`01-RESEARCH.md` (Pattern 3, closing paragraph) states that Drizzle's `migrate()` "applies all `.sql`
files in the folder in filename order" and advises hand-placing the trigger file into the migrations
folder with a sortable name. **Do not rely on that claim.** It is sourced from `01-RESEARCH.md`'s own
LOW-confidence WebSearch tier, and that document explicitly instructs the reader to sanity-check such
claims against the library before locking task-level detail. Drizzle tracks migrations through a
journal in the migrations folder's `meta/` directory; a `.sql` file that is not registered there is
liable to be ignored entirely — producing a migration that appears to exist, reports success, and
never runs.

Task 2 therefore creates the trigger migration through `drizzle-kit generate --custom`, which is the
supported path for hand-written SQL and registers the migration properly. Task 2's acceptance criteria
verify the *outcome* (the triggers exist in `sqlite_master` after `runMigrations`, and they fire),
not the mechanism — so the task is correct regardless of the internal detail.
</research_divergence>

Do not hand-place a `.sql` file into the migrations folder and assume it will run; an unregistered file may be ignored, which would leave you with a migration that reports success and does nothing. Verify registration explicitly, then verify the outcome behaviorally.

    Write the trigger SQL into the generated file. The Postgres original delegates to one shared `refresh_public_mechanic(id)` routine invoked by two triggers. SQLite has no stored functions, so the routine's body must be inlined into each trigger, and — the divergence that determines the count — SQLite requires a separate CREATE TRIGGER statement per event type, where Postgres allows one definition to cover insert, update, and delete together. Two source triggers therefore become **six**:

    On `profiles`: after insert; after update of the three projected columns name, role, avatar_url; after delete.
    On `mechanics`: after insert; after update of the two projected columns specialty, is_active; after delete.

    Name them consistently and predictably, so the count assertion and any future migration can address them — use the pattern `trg_public_mechanics_<source table>_<ai|au|ad>`, giving trg_public_mechanics_profiles_ai, _profiles_au, _profiles_ad, _mechanics_ai, _mechanics_au, _mechanics_ad. Create each with the if-not-exists form so re-running the migration against a database that already has them is harmless.

    Each insert and update trigger body is the inlined routine, exactly mirroring the source: first remove any existing projection row for the affected id, then insert a fresh one selected from profiles joined to mechanics on their shared id, restricted to the affected id, to profiles whose role is the mechanic literal, and to mechanics whose is_active is 1. Select the profile's id, the profile's name, the mechanic's specialty, the profile's avatar_url, and the current timestamp using the same ISO-8601 UTC expression the schema's defaults use. The delete-then-conditional-insert shape is what makes withdrawal work for free: if the row no longer qualifies, the insert's WHERE clause matches nothing and the delete has already removed the stale entry. Do not replace it with an upsert, which would leave withdrawn mechanics listed.

    Each delete trigger body is just the removal for the departing id.

    Two SQLite details that decide whether this works. First, the insert and update triggers address the affected row through the NEW row reference while the delete triggers must use OLD — NEW does not exist in a delete trigger, and a body that references it fails at creation time, not at fire time. Second, `mechanics.is_active` is stored as an integer under the boolean convention, so the trigger's filter compares it to 1, not to a SQL boolean keyword.

    One consequence worth understanding before you write the test: `public_mechanics.id` references `mechanics(id)` with cascade delete, so deleting a mechanics row would clear the projection even with no trigger at all. The mechanics delete trigger is still specified — it mirrors the source and it keeps the projection's correctness independent of the foreign-key pragma being enabled — but do not let that cascade path be the only reason the deletion test passes. Make the withdrawal assertions that actually discriminate be the deactivation and the role-change cases, which no cascade can produce.
