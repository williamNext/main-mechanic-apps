<objective>
Close the session loop the walking skeleton opened. `01-01` proved a user can be created; this plan
proves a user can come back, stay authenticated across a restart of the server, and end their session
deliberately — with the ending actually enforced on every subsequent request rather than merely
reported.

**User story (MVP):** **As a** returning user of any role, **I want to** log in once and still be
logged in when the app comes back, and **I want to** be able to log out and know the session is really
closed, **so that** I am not re-authenticating constantly and not leaving a live session behind on a
device I have finished with.

Purpose: This is the last slice of the phase and the one that turns D-03's design choice into working
behavior. A single long-lived token is what makes "stays logged in across restarts" free, and it is
exactly what makes logout non-trivial — expiry cannot end the session, so a durable revocation record
must. The blocklist table introduced here is checked by the middleware every authenticated request in
this project from now on, so Phase 2's role-based authorization (AUTH-04) extends this hook rather than
replacing it.
Output: Login, logout, and an authenticated identity route; a SQLite-backed revocation store; the
manual admin bootstrap script; and tests that prove both persistence and revocation across a simulated
process restart.
</objective>

<inherited_contract>
Fixed by `01-SKELETON.md` and `01-01-PLAN.md`; consume, do not renegotiate:

| Concern | Fixed decision |
|---|---|
| Token design | Single long-lived HS256 access token carrying `sub`, `role`, `jti`, `exp`. No refresh token, no rotation (D-03, rated **costly** to reverse — already flagged in 01-01, not re-litigated here) |
| Token minting/verification | `signAccessToken({userId, role})` and `verifyAccessToken(token)` from `src/auth/jwt.ts`; verification pins the algorithm to a one-element allowlist. Never call the JWT library directly from a route or middleware |
| Password handling | `hashPassword` / `verifyPassword` from `src/auth/hash.ts` (argon2id). Never compare hashes by hand |
| Revocation storage | The same SQLite database as everything else. An in-memory store was explicitly rejected because a restart would silently un-revoke every token (D-05) |
| Configuration | Every value comes from `config` in `src/config/index.ts`. No module under `src/` reads the environment object — 01-01's verify step greps for this and this plan must not break it |
| App assembly | `buildApp(db, connection)` in `src/app.ts` is the single wiring point used by both the server and the tests |
| Response shape | Auth responses return `{ token, user: { id, name, email, role } }`; `password_hash` never appears at any nesting level |

**One deliberate divergence, introduced here.** The architectural contract stores timestamps as ISO-8601
TEXT. `token_blocklist.expires_at` instead stores an **integer of unix seconds**, because its only
purpose is to be compared against the JWT's own numeric `exp` claim, and a text/number mismatch there is
how a pruning job silently un-revokes tokens. Record this divergence and its reason in a comment above
the table. `revoked_at` follows the same integer form for consistency within the table.

**Table count.** 01-02's acceptance criterion asserted nine tables in `src/db/schema.ts`. This plan adds
`token_blocklist`, making ten. That table is not part of DATA-01's enumerated set — it is session
infrastructure required by D-04 — so DATA-01's nine-table assertions in `tests/db/schema.test.ts` stay
correct as written and must not be edited to accommodate it.
</inherited_contract>

<scope_note>
**Why the seed script and `GET /auth/me` are in this plan and not scope creep.**

`GET /auth/me` exists because AUTH-02 and AUTH-03 are otherwise unobservable. "Stays logged in" and
"session invalidated" are both claims about what happens on *some authenticated request*, and this
project has none until one exists. It is the minimum authenticated surface that makes the two
requirements testable, and it is what Phase 2 attaches role checks to.

`scripts/seed-admin.ts` is locked decision **D-06** and this phase is its only possible home. AUTH-02 is
written as "User (any role) can log in"; proving the any-role claim requires a non-client account, and
public signup can only ever mint a client (D-07). Phase 3's admin endpoints presuppose an admin already
exists, so the bootstrap cannot live there without a circularity. `01-RESEARCH.md` places
`scripts/seed-admin.ts` in this phase's project structure and architecture diagram for the same reason.
</scope_note>

    **Login (AUTH-02).** Add POST /auth/login to `src/routes/auth.ts`, next to signup and sharing its conventions. Validate the body with a zod schema of email and password; strip unknown keys as signup does. Normalize the email by trimming and lowercasing before lookup, matching how signup stored it. Look the profile up by email, verify the submitted password against the stored hash, and on success mint a token with `signAccessToken` and reply with the same `{ token, user: { id, name, email, role } }` shape signup returns. The role in the response and in the token comes from the stored profile row and from nowhere else — no request field may influence it.

    Two rules govern the failure path, and they are the reason to write it deliberately rather than naturally. First, an unknown email and a wrong password must produce an identical response: one shared generic message, one shared status, constructed once and returned from both branches so they cannot drift apart. Second, do not return early when the email lookup misses — verify the submitted password against a fixed dummy argon2 hash instead, so the two paths cost roughly the same wall-clock time. Skipping that makes the response body identical while the response *timing* still answers the question of whether an address is registered. Generate the dummy hash once at module load, not per request.

    **The authenticated path.** Create `src/auth/middleware.ts` exporting `requireAuth`, a Fastify preHandler. It reads the Authorization header, requires the Bearer scheme, and rejects a missing or malformed header with 401. On success it attaches the decoded caller to the request for handlers to read, in a typed way; declare the Fastify request augmentation rather than casting at each use site. Every rejection returns 401 with a generic message that does not distinguish an expired token from a forged one.

    This middleware is deliberately incomplete after this task: it authenticates but does not yet consult a revocation record, because that table does not exist until Task 2. Task 2 completes it. Do not add a placeholder, a stub, or a commented-out revocation branch — leave the code honest about what it currently enforces, and let Task 2's failing test drive the addition.

If the subject no longer resolves to a profile, return 401.

    Add the revocation store, then complete the middleware Task 1 deliberately left honest about its limits.

    **Schema.** Add a `token_blocklist` table to `src/db/schema.ts`: `jti` as the text primary key, `expires_at` and `revoked_at` as not-null integers holding unix seconds. Primary-key-on-jti gives the lookup an index for free and makes double revocation a no-op rather than a duplicate row. Above the table, comment the two decisions a later reader will otherwise question: why these two columns are integers when every other timestamp in this schema is ISO-8601 text (they are compared against the JWT's numeric exp claim, and a type mismatch there is how a cleanup job silently un-revokes tokens), and why this table exists at all (a single long-lived token per D-03 cannot be ended by expiry, so D-04 requires an explicit revocation record, and D-05 requires it to live in this database rather than in process memory).

    Generate the migration for this table the same way 01-02 generated its schema migration, and commit it.

    **Store.** Create `src/auth/blocklist.ts` exporting three functions over the injected database handle. `revokeToken` records a jti together with the expiry taken from the verified token's own exp claim — take it from the token, never recompute it from the current time plus a configured duration, because a token minted under a previous expiry setting would then be under-covered and become usable again. Make it idempotent, so logging out twice is not an error. `isTokenRevoked` answers a single indexed lookup by jti. `pruneExpiredRevocations` deletes rows whose recorded expiry has already passed relative to the current time — and nothing else. This is the function the prohibition in this plan's `must_haves` is about: a row may be removed only once the token it revokes could no longer pass signature verification anyway. Do not add an age-based, count-based, or fixed-retention-window variant, and do not schedule this function to run automatically in this phase; it is a maintenance entry point, and correctness of AUTH-03 does not depend on it ever being called.

    **Complete the middleware.** In `requireAuth`, after the signature verifies and before the request is allowed to proceed, look the payload's jti up in the blocklist and reject with 401 if present. Order matters: verify first, then check revocation, so an unsigned or forged token never causes a database read. Use the same generic 401 message as the other rejection paths, so a caller cannot distinguish a revoked token from an expired or forged one. This check belongs in the one shared hook and nowhere else — every authenticated route in this project, including the ones Phase 2 adds, must pick it up by using `requireAuth` rather than by remembering to call a revocation check of its own.

    **Logout.** Add POST /auth/logout to `src/routes/auth.ts` with `requireAuth` as its preHandler, so a caller must present a currently-valid token to end it. The handler passes the authenticated request's jti and exp to `revokeToken` and returns a success status with no body. Because the route sits behind the same hook, presenting an already-revoked token returns 401 rather than a second success — logout is not idempotent at the HTTP layer even though the store beneath it is, and that is the honest answer.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| mobile client → HTTP API | Untrusted credentials and untrusted bearer tokens cross here; the token is the only identity claim the server receives |
| bearer token → server identity | Everything downstream trusts the decoded payload. Both gates on that trust — the signature check and the revocation lookup — live in one hook, so a route that forgets the hook is unauthenticated |
| `token_blocklist` → session validity | The sole record that a session ended. Any process that deletes from it grants access; this is why pruning is bounded by recorded expiry |
| command line → `scripts/seed-admin.ts` | An administrator password crosses here, and the script writes the only account that can ever create other privileged accounts |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Spoofing | `src/auth/middleware.ts` | critical | mitigate | Tokens are verified only through 01-01's `verifyAccessToken`, whose algorithm allowlist is pinned; the middleware never calls the JWT library directly. Tests assert rejection of a token declaring no algorithm and of one signed with a different secret |
| T-03-02 | Elevation of Privilege | `token_blocklist` pruning | high | mitigate | `pruneExpiredRevocations` deletes only rows whose recorded expiry has passed. A test constructs a long-ago-revoked, far-future-expiry row and asserts it survives — the exact row an age-based cleanup would delete and thereby un-revoke |
| T-03-03 | Spoofing | `POST /auth/logout` durability | high | mitigate | The blocklist is a SQLite table, not process memory (D-05). A test logs out, rebuilds the app over the same file, and asserts the token is still rejected; the same test asserts an untouched session still works, so the restart is not passing by rejecting everything |
| T-03-04 | Information Disclosure | `POST /auth/login` failure paths | medium | mitigate | Unknown email and wrong password return one shared, identically-constructed response, and the unknown-email path verifies against a module-level dummy argon2 hash instead of returning early, so response timing does not answer whether an address is registered |
| T-03-05 | Elevation of Privilege | `scripts/seed-admin.ts` | high | mitigate | Not reachable over HTTP by construction — it is a manually-run script (D-06), it refuses to run when any admin already exists, and it exits non-zero rather than quietly minting a second superuser |
